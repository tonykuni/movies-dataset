自動分類準確度提升報告
— 降低人工校正率

VIA WorkOps · 2026/08/08 · 掛載目標:M1 wop_identifier / identifier_params.json · read-only · run-local

00核心思路

校正率下降不是「模型更聰明」,而是路由順序由精準至模糊:讓確定性規則先攔截,統計歸納只當保底。每一層命中就終止,不再往下傳——進入人工候選池(names propose)的,只剩真正的未知郵件。

◎ 三條鐵律(與既有治理一致)
① 已核對名(names apply)永不被統計覆蓋——人工確認是最高真相。
② 規則優先於統計——names add 自建規則一律先於叢集歸納執行。
③ 每次校正都要「買到」永久性——確認過的 thread/名稱/代碼寫入對映表,同類下次直接命中,同一個錯誤永遠只改一次。

01八層路由瀑布(由精準至模糊)

L0
雜訊過濾池(黑名單)行銷電子報/促銷/系統驗證信 → NOISE-MARKETING / SPAM-PROMO 專用槽直接攔截;促銷關鍵字(限時優惠/早鳥/抽獎/早報)自動降權
攔截後不進分類
L1
主旨/內文案號[PRJ-###]/[THR-####]/[WOP-##] 主旨錨點;主旨漏帶時內文代號補全——引擎同時掃信體提取編號回掛
100%·零校正
L2
Thread 錨定繼承In-Reply-To/References 解析;thr_case_map 曾被人工確認過的 thread,後續所有 Re/Fwd 直接繼承分類——即使對方亂改主旨
100%·確認過即永久
L3
PRODUCT CODE結構化郵件(銀行通知/訂單/發票/系統警示)regex 抽特徵碼 → 生成內部代碼(如 SINOPAC_DEBIT_PAY)→ 強制歸戶;主旨每期變動無妨,代碼不變
98%+·設定一次免校正
L4
組合規則引擎names add 升級支援 AND/OR:寄件者網域 + 主旨關鍵字 + 附件特徵組合(@sinopac.com 且「消費通知」→ 永豐簽帳卡);徹底分開行銷信與正式通知
98%+
L5
網域白名單寄件者網域 → 預設分類/案號對映表;系統信主旨常變、網域不變,第一層特徵最穩定
95%+
L6
已核對名模糊比對與已核對名相似度 ≥ 門檻(建議 90%,rapidfuzz)自動判同案,不進候選;alias 字典吸收異體寫法(永豐 ↔ Sinopac ↔ 永豐銀行)
高·隨核對累積上升
L7
附件指紋附件檔名規則/固定格式(電子交易明細單/發票 XML/結算報表)輔助歸類——分類依據不在主旨的信件由此補洞
輔助訊號
L8
統計/語意歸納(保底)前七層皆未命中才進叢集歸納 → names propose 人工候選池(mouse-only 一鍵核對)
唯一產生校正之處

效果邏輯:校正率 = L8 的流量。前七層每攔截一封,人工候選池就少一封;P0 規則設定完成後,L8 只剩「真正第一次見到的郵件」。

02四個對映表 — 校正買永久性的落點

thr_case_map(加權+衰減+雙向)

  • 加權:人工確認過的 THR↔CASE 對映權重=∞(永久錨定);統計推斷的對映帶信心分數
  • 時效衰減:新互動權重高於舊紀錄,長期演進案件精準續接最新脈絡
  • 雙向增強:同時記 THR↔PRODUCT CODE,同服務同類信歷史記憶直接命中

alias 字典(命名核對迴圈擴充)

  • 核對表允許設別名/縮寫/異體字,一名多寫全部收斂到正典名
  • names propose → 核對表改名 → names apply 迴圈不變;已核對名鎖定最高優先權
  • OpenCC 繁簡正規化先行,再進比對

product_code_map(新增)

  • 語法:names add "永豐簽帳卡消費" --product-code "SINOPAC-DEBIT-NOTIF"
  • regex 從 header/內文抽特徵(特店代號/交易類型/載具類別)自動生成內部代碼
  • 行銷雜訊也代碼化(NOISE-*):攔截即分類,不佔運算

domain_map(新增)

  • 寄件者網域 → 預設分類/專案;與 S5 訊號源同源,升級為第一層確定性規則
  • 與關鍵字組成 AND 條件即為 L4 組合規則
  • 全部 JSON 參數,不改程式(參數 JSON · 模組 Python · UI HTML)

03操作優先順序

優先策略步驟預期效果
P0 立即對高頻日常郵件(銀行通知/訂單/定期報表)設 names add 規則 + 雜訊黑名單池立即解決 70%+ 重複校正;候選池瘦身,人工只看真未知
P1 中期發信帶代號習慣化 + names propose→apply 迴圈持續跑 + thread 確認錨定累積特定案件追蹤命中率趨近 100%;歷史越厚越準
P2 系統網域+regex 組合規則、PRODUCT CODE 抽碼、附件指紋、alias 字典完備徹底消除雜訊干擾;引擎專注核心專案;校正率壓到個位數 %

04與既有模組的接線

本報告機制落點改動
八層路由順序identifier_params.json → routing_priority[]M1 增讀路由序列,逐層命中即終止
四個對映表thr_case_map / alias / product_code_map / domain_mapJSON 檔各自獨立,只增不減;確認寫回由 convergence 既有機制承接
fuzzy 門檻/衰減參數convergence_params.json沿用 auto_accept 體系,加 fuzzy_threshold(0.90)與 recency_decay
雜訊池noise_rules.json + ③頁雜訊槽L0 攔截件入專用槽可回顧,不是刪除(read-only 原則)
內文代號補全M3 reply_parser 共用 token 掃描器主旨/信體同一套編號 regex,一處維護
⚠ 一個要守住的邊界:L3–L5 的「強制歸戶」只適用確定性特徵(代碼/網域/規則)。任何相似度、統計、語意判斷(L6–L8)一律不強判——分歧或低信心就進 ASK,寧可多問一鍵,不可錯歸污染 thr_case_map 與 mining 的 Case ID。錯誤的永久錨定比校正更貴。
