# 批636 · 不刪除,而且保全率要量得出來

## 你的令
> 擷取本文用非OCR / MARKDOWN / OCR 多種擷取法,有時會本文及表格同步擷取;
> 用 LAYOUT 引擎標註類別、次類別、頁數;先還原再把本文修好,斷行間隔修好;
> 一句一行、一標題一行、表格一列一行;表格資料庫;
> 文字修正好並標示是標題、表、本文還是其他;
> **這是一個不刪除修正好本文輸出**;再根據修正好的輸出進行 SUMMARIZE。

## 三道擷取與 LAYOUT 標註,樹上本來就有

我先去看 ENG072 實際落下什麼(不假設欄位名):

| sidecar 欄位 | 內容 |
|---|---|
| `header` / `right` / `body` / `footer` | 四區,周邊資訊區與本文已經分開 |
| `heads` | **GenericLayoutEngine 2.x 標的** `{text, size, level: H1/H3}` |
| `tables` | 逐表逐列 |
| `compare` | **方法之間逐區對照** `{ratio, verdict: AGREE/DIVERGE/BOTH_EMPTY}` |
| `triage` | `DIGITAL` / 稀薄 / 走哪個 backend |

所以 LAYOUT 標註不必重做,**ENG085 是用它不是再造一個**。重抽一次的那一份,跟原本那一份遲早會不一樣。

## 要修的病是量出來的

`VRN_Meeting_Minutes` 這一份:

```
tables[0] = [['#','行動','負責人','期限']]        ← 只有表頭一列
body      = 「1 Action Items 行動項目#行動負責人期限1 ControlCenter 的即時狀態燈號…」
                              ^^^^^^^^^^^^^^^^ 資料列全漏進本文
```

這就是你說的「有時會本文及表格同步擷取」。ENG085 的做法是**把它找回來標成表,不是刪掉**——刪掉就違反「不刪除」。

## 不刪除是硬規矩,而且要量

每跑一份就現場算**保全率**:來源(四區 + 表)的非空白字元逐字比對輸出,掉一個就報出來是哪些字掉了幾個。

理由很簡單:**「修好」如果是靠丟掉修不動的那幾段換來的,那不是修好**,而且從畫面上完全看不出來——行數變少只會像是「整理過了」(LL248)。

**實跑 81 份:保全率全部 100.00%。**

| 類別 | 行數 |
|---|--:|
| 本文 | 3,231 |
| 其他(頁首/右欄/頁尾) | 49 |
| 表 | 11 |
| 標題 | 8 |
| **未分類** | **0** |

## 保全率救了我兩次

### ① 殘片比對只比單格
病灶是**整列**被黏過去(`#行動負責人期限`)。逐格比的話 `#` 太短被濾掉、`行動` 又不在行首,一個都對不上,那一行就被判成本文 —— 而 SUMMARIZE 會把表頭當句子讀。改成以「列」拼起來比。

### ② 標題黏在行中,而我的第一版切法會砍字
`…會議紀錄VRN Fetch v4 — 設計審查會議日期…` 裡那個 H1 卡在中間,只比行首抓不到。

補上行中比對之後,第一版在 `line.find(標題)` 回 `-1` 時**還是從 0 砍掉 `len(標題)` 個字**
—— 保全率當場 **100% → 96.97%**。

會發生是因為原字裡夾著零寬或全形:正規化之後兩邊一樣,原字裡卻沒有那一串。

> **比對用正規化,切割用字面**;字面找不到就整行留著。
> **留一行沒切開的,比切壞一行好** —— 沒切開看得出來,切壞了看不出來(LL249)。

**兩個坑都是 ㊀ 在真資料上抓到的,夾具太小都沒照出來。**

## 另外兩件

- `1.` `2.` 這種光禿禿的編號被句末的 `.` 切成獨立一行,「一句一行」就變成「一個號碼也一行」——編號要黏回它後面那一句。
- CJK 硬斷接回,但**英數不接**:`Q2\n2025` 接起來會變成 `Q22025`。
