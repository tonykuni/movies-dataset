# 批698:沒掛在門上的引擎,對操作員而言等於不存在

## 一、為什麼有這一批

批697 把資料樞紐 `CGC_MDL179` 做出來了,`collect()` 契約也寫好並自測過 —— 然後我在 PR 裡自己寫下:

> 掛進 VCGC `SUBSYS_PORT`：`collect()` 契約已備妥並自測過,但改 MDL149 是另一版號;本批先把引擎與界線立住。

那句話當下是誠實的(不亂擴 PR),但它留下的狀態很具體:**樹上有一支跑得動的引擎,而中央控管台不知道它存在**。

這個系統對這種狀態有前例。批647 的 `VIA_HTML_UI`:在 main、**冊上沒有、沒有梭**。一支沒掛在門上的引擎,操作員不會從任何一個入口看到它,所以它的綠燈跟沒有是一樣的。

## 二、做了什麼

`CGC_MDL149` v0123 → **v0124**,開第三扇門:

```
[VIA:SYNC-PORT:v0100]  _SYNCPORT / _syncport() / sync_hub()   + sync 動詞  + ㉚ 一檢
```

形狀**逐字照** `_invport()` / `tool_inventory()`(第二扇門,委派給 `CGC_MDL178`)。

**只開埠,不搬實作。** 對帳、雲端掃描、內容定址全部留在 `CGC_MDL179`;本台只做兩件事:解析尾版、原樣端上來。

## 三、㉚ 比 ㉙ 多釘一件:誠實態不准被改寫

㉙ 釘的是「不准把實作抄進來」。㉚ 照抄那個釘法,另外釘一件它沒釘的:

> 樞紐回 `GATED` / `FIRST_RUN` / `ABSENT`,本台就報 `GATED` / `FIRST_RUN` / `ABSENT`。
> **把它們壓成 `GREEN` 或 `RED`,就是在門上偷偷立第二把尺。**

這條值得單獨釘,因為它是最容易「好意造成」的那一種錯:門為了讓畫面乾淨,把六種誠實態壓成紅綠兩種 —— 而壓縮的那一刻,`GATED`(缺機制,是規矩)和 `RED`(真的壞了)就分不出來了。

實跑證明它沒壓:

| 端點 | 功能面 | 資料面 |
|---|---|---|
| `self` | GREEN | GREEN |
| `datahome` | **ABSENT** | SKIP |
| `onedrive_api` / `gdrive_api` / `dropbox_api` | **GATED** | **GATED** |

## 四、自審:我自己寫的那條檢,括號寫得太鬆

㉚ 第一版的判定寫成 `A and B or C`。它**跑起來是對的**,但 `and` / `or` 的優先序讓這條檢**看起來嚴、實際上寬** —— 只要 `state == "BROKEN"` 就整條為真,連「來源是不是 MDL179」都不必看。

這不是紅燈,是一條**將來會鬆掉的檢**。改成三段各自加括號:

```
(ABSENT 且講得出因由) 或 (BROKEN 且講得出因由) 或 (來源是 MDL179 且態在誠實態集合內)
```

凡是檢的判定式裡同時出現 `and` 和 `or`,括號就要寫出來。省下的那幾個字元換來的是「這條檢到底在驗什麼」變得看不出來。

## 五、順帶更正一句本來就在說謊的敘述

自測格裡 VCGC 那一站寫「二十八檢」,而 `v0123` 早就是**廿九檢**。

**這一條不是本批弄壞的,是之前就停在舊數了。** 站照樣會綠(只驗 rc0),所以沒有任何一盞燈會照出它;會被誤導的是讀的人。本批一起改成「三十檢」。

這已經是這幾批第四次碰到同一族問題(批695 / 696 / 697 / 698)。共同形狀是:**站名是敘述,不是斷言**,所以它錯了不會紅。

## 六、界線 —— 三件我沒做,因為它們需要你的手

操作員說「依你建議持續進行」。那句話授權的是**我列出來、而且我做得到**的下一步,不是以下三件:

| 沒做 | 為什麼一句「持續進行」不夠 |
|---|---|
| 裝件(`INSTALL ×5`) | 要開同意閘。**不代設 `VIA_NET_CONSENT`** —— 一句泛稱的「繼續」不是你親手貼上那一行 |
| 短令 `via-hub` | 在 `.ps1` 裡。**L70 要逐次許可**,而「逐次」的意思就是針對這一次、這一支檔 |
| 主線陸券回歸 | 那是別條線的檔(`bee8a683` 經 PR #70 帶回)。**只報不裁** |

## 六之二、Codex 兩條:我在同一個 commit 裡違反了自己剛立的 LL360

PR 開出去之後 Codex 貼了兩條 P2。**兩條是同一個根因的兩個出口:硬壞掉被報成軟的。**

| findings | 我的錯 | 修法 |
|---|---|---|
| 載入失敗時要保留 `BROKEN` | `_syncport()` 在**兩種**情形回 `None`:檔不在、以及檔在但 import 期就炸。舊寫法一律報 `ABSENT` —— **「裝了但壞掉」被說成「沒裝」**,`rc` 還回 3 而不是 1 | 讀 `why`,前綴是 `BROKEN` 就報 `BROKEN` |
| 要認得帶後綴的 `BROKEN` | `collect()` 回的是 `BROKEN OSError:...`,不是剛好等於 `"BROKEN"`。`state in ("ABSENT","BROKEN")` 整個漏掉,最後回預設 rc 2 —— 自動化那端會當成「這次沒資料」繼續跑,而真相是引擎炸了 | 抽 `_hub_broken()` **比前綴不比相等**;rc 也改走委派 |

第一條諷刺得很精準:**我在這一批立了 LL360「一扇門最容易犯的錯不是抄實作,是把態壓扁」,然後在那條律描述的那個函式裡,自己第一個犯。** LL339 說自己剛立的律最先違反的人通常是自己 —— 這次的樣本是我本人。

㉚ 因此加了**反面控制**:把埠的記憶換成「載入失敗」的樣子,**實跑** `sync_hub()`,必須拿到 `BROKEN` 且 `why` 帶得出 `ImportError`。不是讀原始碼,是逼那條分支真的走一次。

## 八、教訓

- **LL359:一支沒掛在門上的引擎,對操作員而言等於不存在。** 「先把引擎立住,掛門下一批」是合理的分批,但那個中間狀態要記成待辦並且真的收掉,否則它跟沒做完是一樣的。
- **LL360:一扇門最容易犯的錯不是抄實作,是把態壓扁。** 為了畫面乾淨把六種誠實態壓成紅綠兩種,`GATED`(缺機制,是規矩)和 `RED`(真的壞了)就分不出來 —— 這是好意造成的假訊號,所以要單獨釘一條檢。
- **LL361:檢的判定式裡同時有 `and` 和 `or`,括號一定要寫出來。** 沒寫括號的檢可能今天是對的,而它「看起來嚴、實際上寬」,鬆掉的那天不會有人發現。
