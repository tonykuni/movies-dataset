# 批726 — 差 2 檔的那句話,和我一直用 grep 重造的那張總表

---

## 一、「差 2 檔」不該讓人去重跑整條鏈

工作站實測,⑨ 市場寬度從 FAIL 變成 SKIP,句子是:

```
2026-09-18:該日在庫 1988 ≠ 庫標的宇宙 1990 = 99.9%
= 因子鏈未跑全宇宙,缺料不是壞;via-vdffetch(3a/3b 因子段)後複判
```

**99.9% 配上「因子鏈未跑全宇宙」,會讓人去重跑整條鏈。**
但真相可能只是那 2 檔天生沒有 —— 新上市、停牌、下市當日。
重跑一整條因子鏈也補不出來。

所以讓它**點名**:

```
差 2 檔:6548、8478 —— **先看這幾檔是不是天生沒有**(新上市/停牌/下市當日),
是的話重跑整條因子鏈也補不出來;不是才 via-vdffetch(3a/3b 因子段)後複判
```

那段 SQL 容器裡沒有 `features_daily` 可跑,所以**用記憶體庫造了同形狀的資料驗過**:
5 檔宇宙、目標日 3 檔 → 正確點名 `D`、`E`,而「天生算不出(ma20 為 NULL)」的 `B`
**分得開**、不會混進來。

> 沒驗過的 SQL 不推 —— 尤其是這種「紅的時候才會跑到」的分支。

## 二、操作員令「善用 VCGC 工具節省 TOKEN」

量了才知道差多少:

| | 成本 |
|---|---|
| `vcgc status` | **15 行 · ≈609 token** —— 政策庫/邏輯庫/因子庫/VRN·VDF 系統燈/資料庫/引擎調度/多矩陣/環境工具/環境復原/VTMRA/中央治理家族/註冊稽核/台帳 |
| `vcgc audit` | **2 行 · ≈75 token** |
| 我過去的做法 | 每批 5–10 次 grep 拼湊,**三到五千 token**,而且拼出來的還比較窄 |

**五到八倍。** 而且省下的不是最重要的部分 ——

## 三、它一跑就照出我沒看到的東西

```
邏輯庫 OK:件 60 · {'SUCCESS': 2, 'PARTIAL': 2, 'FAIL': 56}
中央治理家族 RED · 成員 {'console': 'RED', …}
資料庫:資料家 ABSENT(DATAHOME_CATALOG_latest.json 不在)
環境工具 PLAN:{'ENV_ABSENT': 69, 'UNROUTED': 59}
```

這些**全格子都是綠的**(344 站真 FAIL 0)—— 因為格子量的是「引擎自測過不過」,
而 VCGC 量的是「**系統現在是什麼狀態**」。兩把尺看的不是同一件事。

> 我用 grep 重造了一張比較窄的總表,然後因為那張表上沒有這幾欄,
> 就以為系統沒有這幾件事。

## 四、這一批的律

**LL430 先問樹上有沒有現成的總表,再決定要不要用 grep 拼一張。**
這跟 LL404(開新尺之前先問有沒有人量過)是同一條,但更難察覺:
LL404 擋的是**重複造輪子**,LL430 擋的是**造一個比較窄的輪子然後以為那就是全部**。
`vcgc status` 15 行給的面,比我 10 次 grep 拼出來的更寬、更便宜。

**LL431 紅燈給的補救動作,要配得上它報的數字。**
99.9% 配「重跑整條鏈」不成比例。
差幾檔就點名哪幾檔 —— 看的人才分得出「補得回來」和「天生沒有」。

## 五、本批往後的做法

每批開頭先跑 `vcgc status`(609 token),而不是散彈式 grep。
要細節再用 `CGC_MDL158 read/slice` 只取那一段 —— 這兩支合起來就是 CLAUDE.md
那條「先讀骨架卡,不讀原始碼」的完整版:
**先看總表,再看骨架卡,最後才看原始碼。**
