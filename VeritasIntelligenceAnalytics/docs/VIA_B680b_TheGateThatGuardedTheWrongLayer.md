# 批680b · 門裝對了邊,卻裝錯了層

批680 我寫下一句話,當時覺得是誠實,現在看是**沒查到底**:

> 批679 已經把冊清乾淨了,所以今天這個閘在真跑裡一次都不會觸發。

「今天不會觸發」聽起來像是「暫時沒料」。Codex 在 PR #59 照出真相:
**它不是暫時不會觸發,它是裝在一個永遠碰不到料的位置。**

## 一 · Codex 說的那一條,驗過是真的

> 文內寫被拒機構名時,`_safe_broker_raw()` 會先命中較短的合法別名並回傳它的正典名,
> 只檢查那個正典名就漏掉了拒絕清單上的那一條。

逐條對樹驗過才動手,不是看了就信。實跑(批680 的 v0110):

```
本報告由中信證券研究部出具  → ('CTBC', '文內')
```

`中信證券` 在操作員批413 的拒絕清單上;冊上沒有這一條別名(批679 已清),
於是最長別名優先命中了**合法的**「中信」(2 字)→ CTBC。
**一家被拒的陸券,被記成台灣的中國信託。**

而且不只這一條。同一個根因往下掃,還有兩條:

| 文字 | 批680 的答案 | 為什麼 |
|---|---|---|
| `國泰君安證券研究` | `CATHAY` | 被較短的合法別名「國泰」接走 |
| `海通證券研究所` | `(None, '無')` | 冊上已清 → 解不出正典名 → 閘根本沒被呼叫到 |

第三列才是病根:**批680 的閘只擋得住「已經解出來的被拒正典名」,
而被拒的料已經不在冊上了** —— 所以它擋的是一個永遠不會出現的東西。
「一個永遠不觸發的閘等於沒有閘」這句話我在批680 自己寫了,然後用正控**假造**了一次觸發,
證明了「如果它觸發,它會咬」—— 卻沒有問「它到底會不會被觸發」。

## 二 · 修法:不是另造一把尺,是把名單丟進同一把尺

樹上原本就有一把尺:`_safe_broker_hit()` 的**最長別名優先**
(CJK 直接子字串 · 拉丁詞界 · ≤3 字拉丁要大寫獨立詞)。
批680 的錯是在那把尺**之後**另外加了一道檢查;正確的作法是把拒絕清單
**當成候選別名丟進同一把尺一起比長短**:

```
文內命中的被拒名,只要不比命中的合法別名短,就是它贏。
```

四個方向一次說完:

| 情況 | 誰贏 | 例 |
|---|---|---|
| 被拒名**比**合法別名**長** | 被拒的贏 | 4 字被拒名 ⊃ 2 字合法別名 → 拒絕 |
| 被拒名**比**合法別名**短** | 合法的贏 | 2 字被拒名 ⊂ 5 字合法券商名 → 放行 |
| 只有被拒名命中 | 被拒的贏 | 冊上已清也擋得住 |
| 都沒命中 | 查無 | 原樣放行 |

第二列是**不可省**的:拒絕清單上那個兩字的曖昧桶(操作員批413 列它,正是因為它同時
指向兩家不同的外資),如果照「出現就擋」去做,會把兩家**合法**的大行一起連坐,
而那正是批679 花力氣拆開、並且釘住期待值的東西。

## 四 · Codex 的第二條:我在同一個地方犯了第四次

> 行為探針應該從**當前的**拒絕清單取值,而不是寫死一個。

`CGC_MDL176.gate_behaviour()` 裡是 `lambda: "GF"` —— 我打字打進去的。
**LL336 是我在批680 剛立的,立在同一個檔裡,然後在同一個檔的另一個函式裡違反它。**

而且改掉之後還撿到一個更大的好處:新的閘**餵真文字就會觸發**,
所以那段 monkeypatch 整個不需要了:

```
批680  把解析器換成假函式 → 量的是「如果解出被拒名會怎樣」(而那條路現在不會發生)
批680b 直接餵真文字逐條試 → 量的是「真正的路會怎樣」
```

假解析器量不到真正的路,而**真正的路正是出問題的地方**。

所以格子取 **v0436**,並且把兩條側線多出來的 **4 站原樣併進來**
(用**引擎落點**當鍵,不是敘述字串 —— 有幾站兩邊敘述不同但落點相同,
照字串併會併出重複站)。那兩支引擎只在他們分支上,本分支 `newest()` 找不到 → 誠實 SKIP。

**不這樣做的話:他們任何一條先併,我批680 加的 `SUP_MDL015` 站就會在尾版律下整個消失,
而且不會有任何一盞燈紅** —— 因為格子跑的是「這一份檔上有的站」,不是「應該要有的站」。

順帶量到一件同型的事:側線也在用 `批681` / `批682B` / `批685` 這些批號。
**批號跟版號一樣是跨分支的共用資源**,所以這一批照我自己 批679b/c/d 的慣例叫 `批680b`,不去搶號。

## 五之二 · 併站的時候我把 4 站插成了死碼,格子的站數當場照出來

第一版的併法是**文字啟發式**:找到最後一個 `    add(`,再找它後面第一個非縮排行當插入點。
最後一塊切到檔尾,於是「後面第一個非縮排行」不存在,插入點落到 **EOF** ——
那 4 站被寫在 `if __name__ == "__main__": sys.exit(main())` 底下,**是死碼**。

AST 解析會過、`python -m py_compile` 會過、檔案看起來也正常。
抓到它的是**格子自己的站數**:

```
預期 290 站   實際印出 286 站
```

改成用 **AST 取「註冊函式裡最後一個 `add()` 呼叫」的 `end_lineno`**,
並且在寫檔前斷言 `add()` 呼叫數必須剛好 +4。

> 這跟批679 的 ③(升版註記插到 docstring 前面)是**同一個錯**:
> 用文字找位置,而不是用結構找位置。兩次都在同一個地方栽 —— 所以這次加了**數量斷言**,
> 不只靠「看起來對」。

## 五之三 · 順手照出格子自己的一個既有缺陷(不是這一批造成的)

平行跑(4 工)出現 6 盞紅,全部是同一句:

```
_duckdb.IOException: Could not set lock on file "…/mega/vdf_tw_market.duckdb":
Conflicting lock is held in /usr/bin/python3.11 (PID 3999)
```

**格子自己的平行工彼此搶同一個 DuckDB 的寫鎖。** 批680 那一跑剛好沒撞上,這一跑撞上了
——所以它是**時序相依**的,不是我這一批造成的,但也**不是 flake**:
只要那幾站同時被排進同一批工人,它就一定紅。

`--serial` 是格子自己備的退路,這一批的驗收數字用序列跑。
**根治要讓那幾站以 `read_only` 開庫、或在同一庫上加排程互斥** —— 那是另一批的事,
這裡只把它量出來、指名、留痕,不順手改別人的站(L87)。
